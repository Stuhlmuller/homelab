# Argo CD Image Inventory

Tags: #operations #argocd #security #images

## Scope And Ownership

The [#791 coverage finding][coverage] omits three configured Argo CD image
identities, not three confirmed running Pods. This audit uses repository base
`b408a858877e3a53c5bbe9da93a927ae6dfabc0e`; the bootstrap declarations are
unchanged in scanner draft `021a510698be3e7f88bd672301717e4f6e76841b`.

The [catalog unit][catalog], generated by [the explicit stack][stack], installs
Helm chart `argo-cd` **9.5.15**, whose [appVersion is v3.4.2][chart]. It supplies
no image overrides. The cached exact chart's [values][values] and templates
establish these consumers:

| Image family | Chart-created consumers |
| --- | --- |
| Argo CD v3.4.2 | Application-controller StatefulSet; API server, repo-server, ApplicationSet and notifications Deployments; repo-server `copyutil` and Dex init containers; Redis secret-initialization hook Job. |
| Dex v2.45.1 | `argocd-dex-server` Deployment's main container. |
| Redis 8.2.3-alpine | `argocd-redis` Deployment's main container, using `ecr-public.aws.com/docker/library/redis`, not a presumed Docker Hub alias. |

Argo CD's shared image uses `global.image.repository` and the
[`global.image.tag` / chart-appVersion fallback][default-tag]. Dex and Redis
use their component repository/tag pairs. Redis HA, Redis exporter, commit
server and the extension installer are disabled and add no identities here.
The Redis initialization Job uses **Argo CD**, not the Redis image.

These workloads belong to the Terragrunt-managed Helm release. The
[self-management Application][self-management] manages the separate repository
Kustomize path; it does not install or upgrade the Helm release's images.

## Manual Scan Results

A separate authorized audit scanned exactly the **four** immutable references
above once, sequentially, on **2026-08-30, 04:15:14–04:15:43 UTC**. Trivy
**0.74.0 / Go 1.26.7** ran from an empty directory with inherited credentials
and scanner settings cleared, explicit empty Docker/Podman configurations,
remote-only `linux/amd64` pulls, five-minute limits and no exceptions. No
container was executed; no live endpoint, registry login or runtime mutation
was used. Public ECR does not match Trivy's private-ECR credential-provider
predicate; metadata credential lookup was additionally disabled.

Policy: `--scanners vuln --severity HIGH,CRITICAL --ignore-unfixed`,
`--list-all-pkgs --format json --exit-code 1`, `/dev/null` configuration and
ignore file, and final `--` before each immutable reference. DB, Java-DB and
version updates were disabled. Every report's reference, index digest,
configuration digest and `linux/amd64` platform matched the metadata proof.
All four returned **1**, had positive package inventories and failed the gate.

| --- | --- | ---: | ---: | ---: | ---: |
| Configured Argo CD v3.4.2 | Ubuntu 25.10 | 591 | 53 | 2 | 151 |
| Configured Dex v2.45.1 | Alpine 3.23.3 | 286 | 63 | 4 | 127 |
| Configured Redis 8.2.3-alpine | Alpine 3.22.3 | 22 | 15 | 2 | 17 |
| Existing #850 Argo CD v3.4.8 | Ubuntu 26.04 | 604 | 50 | 2 | 155 |

HIGH/CRITICAL counts use unique `(VulnerabilityID, PkgName, FixedVersion)`
tuples within each image. Raw rows and package records include repeated
entries across binaries. Positive inventory is not complete application
coverage: Redis has only an OS-package target, not a Redis-binary target.
All findings are package/module-version matches, not reachable-exploit or
current-deployment proof.

The candidate retains **52 of the configured image's 55 tuples** and removes
three OS-package tuples. It is **not a passing security replacement** under
this policy. Both Argo images report Go 1.26.0 in `argocd`, 1.25.3 in `git-lfs`,
1.24.11 in Helm and 1.24.0 in Kustomize; the candidate also contains Pebble
built with Go 1.26.2. Dex and its entrypoint report Go 1.26.0, while bundled
Gomplate reports Go 1.25.6. The full module inventory remains in the evidence.

### Critical Matches And Qualifications

- [CVE-2025-68121][go-advisory]: `stdlib` in both Argo images' `git-lfs`, Helm
  and Kustomize binaries (1.25.3 / 1.24.11 / 1.24.0) and Dex's Gomplate
  (1.25.6). Reported fix floors: 1.24.13, 1.25.7 or 1.26.0-rc.3.
- [CVE-2026-33186][grpc-advisory]: `google.golang.org/grpc` 1.72.1 in both
  Argo images' Helm binary; 1.79.1 in Dex and 1.77.0 in Gomplate. Reported
  fixed version: 1.79.3. Bundled-library presence does not establish that an
  affected gRPC server path is exposed.
- [CVE-2026-31789][openssl-advisory]: `libcrypto3` and `libssl3` 3.5.5-r0 in
  Dex and Redis, fixed at 3.5.6-r0. The reports use Alpine Secdb package data
  but `SeveritySource: nvd`, CVSS 9.8 / CRITICAL. **OpenSSL rates this LOW**:
  the overflow requires a 32-bit platform printing or logging an untrusted
  certificate larger than 1 GB. The selected images are Linux/amd64, and the
  reported library packages are `x86_64`; no 64-bit exploit is established.
  Keep the raw policy counts, without suppression or a definitive binary
  reachability verdict. The independent HIGH findings still fail both images.

These per-advisory fix floors are not complete upgrade recommendations.
Trivy marks the configured Argo image's Ubuntu 25.10 base `EOSL: true`;
[Ubuntu confirms end of support on 9 July 2026][ubuntu-eol]. Its frozen OS
advisory coverage cannot establish a complete future vulnerability count.
The candidate's newer OS does not clear its remaining bundled Go findings.

## Next Step And Existing Scope

Use #788/#850 for the Argo CD, Dex and Redis remediation already in scope;
no duplicate issue or parallel pin PR is needed. Preserve the staged rollout
and policy-enforcement gates, but do not accept the proposed image baseline
as clean. Future candidate work needs supported OS and bundled dependencies,
the same exact-image scan policy, and separate compatibility/rollout review.
No further candidate resolution, exception or image change was performed.

Keep continuous inventory coverage under #791: the current scanner reads
repository YAML and literal operator-script images, not the bootstrap HCL or
remote chart defaults. HCL tag pins alone therefore do not add these images
to its input. A bounded follow-up must prove extraction from exact evaluated
bootstrap Helm values or rendering, including the shared init/hook consumers,
before treating these three families as continuously scanned.
