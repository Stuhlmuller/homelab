# n8n Desired State

n8n runs as a self-hosted automation service. Its editor keeps
`https://n8n.stinkyboi.com` through private Tailscale mesh and Traefik after the
[staged DNS cutover](../traefik/CUTOVER.md). Legacy Octelium routes remain only
until replacement acceptance.

n8n uses the dedicated `n8n-postgres` support app for workflows, credential
metadata, user records, and execution history. It still persists
`/home/node/.n8n` on the default NFS StorageClass for the instance config,
encryption-key settings, and file-backed runtime data.

The Terragrunt-generated encryption key comes from AWS SSM Parameter Store
through External Secrets as `N8N_BOOTSTRAP_ENCRYPTION_KEY`. Both the app and
the staged one-time workflow-migration Job export it as `N8N_ENCRYPTION_KEY` only
when `/home/node/.n8n/config` does not exist yet, so a restored or
already-initialized PVC keeps using the key in its persisted settings file
instead of crashlooping on an accidental mismatch.

## Runtime Security

The pod pins the upstream n8n `node` identity at UID/GID `1000`, uses the
`RuntimeDefault` seccomp profile, disables privilege escalation, and drops all
Linux capabilities. The PostgreSQL readiness init container inherits the same
restrictions but uses the repo's established unprivileged UID/GID `65534`; it
only reads the mounted client secret and runs `psql`, so it does not need root
or write access to the n8n data volume.

## Runtime Secret Contract

- `/homelab/n8n/encryption-key`: n8n first-boot encryption key generated by
  Terragrunt/OpenTofu and stored in AWS SSM. After first boot,
  `/home/node/.n8n/config` is the runtime source of truth for the persisted
instance key; do not rotate the SSM value without following an n8n-supported
  key rotation or data migration path.
- `/homelab/n8n/postgres-app-password`: n8n database user password mounted from
  `n8n-postgres-client` and read through `DB_POSTGRESDB_PASSWORD_FILE`.
- `/homelab/n8n/litellm-token`: dedicated inference-only gateway key. External
  Secrets renders it into `CREDENTIALS_OVERWRITE_DATA`, so a blank `openAiApi`
  credential resolves to `http://litellm.ai.svc.cluster.local:4000/v1` without
  serializing the key in a workflow.

The n8n Deployment no longer runs the AI migration as an init container.
`migration-v1.values.yaml` contains the guarded, versioned Job but is
**not** listed in `IaC/homelab/us-west-2/apps/n8n/stack.hcl` Helm valueFiles.
The current GitOps render contains no migration Job and this availability fix
makes no workflow database edits. A read-only PostgreSQL query on 2026-10-24
found all three inventoried model nodes already set to `openrouter/free` and
`litellm-managed`; one workflow is active and two are inactive.

A separate activation PR may add the staged file to Helm valueFiles if a
restored or stale database needs migration. Before that PR merges, verify a
paired off-NAS PostgreSQL logical dump and n8n PVC backup plus a restore path.
The [database notes](../n8n-postgres/README.md#backup-and-restore) show a
`pg_dump` command but do not yet establish this paired backup receipt. The
staged Job uses exact workflow/node IDs and previous settings as guards; it
skips missing or edited workflows, fails on list/export/parse/import errors,
and republishes only previously active workflows. It inspects the LiteLLM
credential only when a workflow needs migration. A matching existing credential
with blank stored data is preserved; an absent one is created with blank data.
The decrypted inspection uses container memory (`/dev/shm`) and removes its
temporary file without logging credential values. Inspection failures,
unexpected metadata or nonblank stored data stop the Job before workflow
import. This avoids n8n's same-ID credential import overwrite on retries or
restored DBs; type-wide credential overwrites fill only blank fields.
Credentials and workflow exports retain n8n's required one-element JSON arrays.
The key never enters workflow JSON. Run `nix develop --command python3 -I
scripts/ci/n8n-ai-migration-check.py` to exercise these cases.

When activated, Argo CD applies the Job at sync wave 1 after n8n is healthy and
its PostgreSQL schema exists. Required affinity places the Job on n8n's node
for the existing `ReadWriteOnce` NFS PVC. The Job uses the n8n service account,
file-backed PostgreSQL client secret, and persisted config key; the bootstrap
key applies only when `/home/node/.n8n/config` is absent. Its stable versioned
name means ordinary n8n restarts and Argo resyncs do not rerun a completed Job.
Failures remain visible in Job status and logs while the Deployment serves.
`N8N_AI_MIGRATION_APPLIED` logs only workflow ID, prior active state, and
`restart_required`. If an active workflow changes, a separately reviewed
GitOps Deployment revision must restart n8n before the published change is
live. Verify a real workflow/Langfuse generation before retiring the AWS key.
Rollback needs the paired database dump and n8n PVC restore; editing the Job
cannot undo database changes.

## Staged signed Emergency callback

The GitHub Emergency workflow (`AARG1VWHRxowXlSU`) currently starts with an
unauthenticated generic Webhook node. Its existing GitHub hook `636944763`
uses form encoding without a signing secret. Before Traefik containment on
2026-10-31, a fresh HTTP 200 delivery had no `X-Hub-Signature-256` header;
HTTP success did not authenticate the callback.
`scripts/n8n-github-webhooks.py --require-delivery`
now rejects such an unsigned delivery. Header presence proves GitHub signed a
delivery, while the receiver's HMAC check comes from the n8n trigger.

`migration-github-trigger-v1.values.yaml` stages a one-time Job. It is absent
from the n8n Helm valueFiles and Kustomize resources, so this source change
does not edit the workflow or register a hook. The Job requires the exact
active six-node graph, original parameter fingerprints and seven inventoried
expression locations. It replaces only the old Webhook node with n8n 2.43.7's
native GitHub Trigger, copies the existing `githubAppApi` credential reference,
and changes those expressions from `$json.body.payload` to `$json.body` for
the trigger's JSON event body. Drift aborts before import; an already migrated
graph is a no-op. The new node ID path is
`/webhook/f3e12cbd-1d01-4ef0-b24e-d68741ea898b/webhook`, distinct from the
old path. The pinned trigger creates a random signing secret, configures the
new GitHub hook with JSON content, and rejects invalid signatures before the
workflow runs. It cannot adopt or delete the existing generic hook.

Before a separate activation PR includes this values file, verify a paired
off-NAS PostgreSQL logical dump and n8n PVC backup with a restore path, and
confirm that the existing GitHub App installation credential has repository
`Webhooks: write` permission. Run
`nix develop --command python3 -I scripts/ci/n8n-github-trigger-migration-check.py`
and render the proposed Helm values. Activation imports and republishes the
workflow. In n8n 2.43.7, CLI import first deactivates it; the Job compares the
full imported node graph before publishing and checks active readback after.
A failed import or publish can leave the workflow unavailable, so the paired
restore is required. A separate reviewed GitOps Deployment revision restarts
n8n to load the published version. Verify the new signed hook and a fresh
delivery before retiring the old unsigned hook through a reviewed
repository-owned helper change. Keep Traefik's old-path exclusion in place
through that verification and retirement; the new path is not excluded. The
current callback helper still targets old hook `636944763` and cannot verify
the new hook until that follow-up is added. Rollback requires the paired
database and PVC restore; removing the Job does not undo the workflow edit.

## Access Contract

- Editor/UI: `https://n8n.stinkyboi.com` through private Tailscale and Traefik.
- Internal self-API: `http://n8n.automation.svc.cluster.local:5678/api/v1`,
  limited to the `automation/n8n` service account and n8n API-key authentication.
- Public callbacks: `https://n8n-webhook.tail67beb.ts.net` through Funnel and
  Traefik, only `/webhook`, `/webhook-test`, and `/webhook-waiting` paths.

`WEBHOOK_URL` advertises the Funnel host. Converge and verify that route before
n8n rolls out, because active integrations can register hooks on startup.
Keep editor, static-asset and API routes private. Internal self-API calls use
plain HTTP on the Service's port `5678`; TLS terminates at Traefik, so an HTTPS
Service URL fails. The workload AuthorizationPolicy allows the n8n principal
to call itself without widening other workload access.

Move the surviving external registration from `n8n-webhook.stinkyboi.com` to
the Funnel host only after the [callback cutover gates](../traefik/CUTOVER.md).
Temporary [Traefik containment](../traefik/README.md) denies the unsigned
Emergency Bot webhook path at the Funnel edge. Hook `636944763` returns 404;
other n8n webhook paths stay routed. Do not count Emergency deliveries as
accepted or run the helper cutover while this exclusion is active.

The helper previews the Github Emergency Bot hook `636944763` and the exact
retirement of unused Codex Review Helper hook `589400612`:

```sh
python3 -I scripts/n8n-github-webhooks.py
python3 -I scripts/n8n-github-webhooks.py --retire-helper
```

Its guarded `--execute` changes only the Emergency hook URL, preserving its
path, events, and settings. It requires root 404 and a safe OPTIONS 204
response for that POST-only hook; it never POSTs or triggers redelivery.
`--retire-helper --execute --expected-sha REVIEWED_MAIN_SHA` removes only the
reviewed helper hook after a fresh successful Emergency delivery. Here
`REVIEWED_MAIN_SHA` is the full reviewed current `main` commit. Repeating it
after verified absence is a no-op. `--require-delivery` requires the retired
ID and callback path to be absent, plus a newer successful Emergency delivery
with a SHA-256 signature header after its saved cutover receipt. It does not
prove the receiver validated that signature. Historical success does not
establish current callback acceptance. Keep the legacy Tunnel route until the
surviving Policy Bot and Emergency callbacks pass their fresh delivery checks.

## Database Readiness

The pod uses `DB_TYPE=postgresdb` and waits for an authenticated connection to
`n8n-postgres.automation.svc.cluster.local:5432` before starting n8n. If the
wait init container fails, inspect the `n8n-postgres-auth` and
`n8n-postgres-client` ExternalSecrets, then verify the `n8n-postgres`
StatefulSet and PVC.

Switching from the older SQLite-backed desired state does not automatically
import rows from `/home/node/.n8n/database.sqlite`. Export workflows and
credentials before rollout if the existing SQLite contents must be preserved.

## Database-Aware Health Checks

The startup probe uses `/healthz`, which confirms the n8n process is serving
without terminating a legitimate long-running database migration. After
startup succeeds, readiness and liveness use `/healthz/readiness`, which also
checks database readiness. A PostgreSQL interruption therefore removes n8n
from Service endpoints and, after three failed 30-second liveness checks,
restarts n8n so it rebuilds a stale PostgreSQL connection pool. The init
container waits for an authenticated database connection before the replacement
process starts.

Do not change the readiness or liveness probes back to `/healthz`: that endpoint
can continue returning HTTP 200 after n8n has closed its database pool, leaving
webhooks to return HTTP 503 `Database is not ready!` until the process is
replaced.

After a separately approved migration activation, inspect the Job without
changing it:

```sh
kubectl -n automation get job/n8n-migrate-ai-workflow-v1
kubectl -n automation logs job/n8n-migrate-ai-workflow-v1 -c migrate
```

Expected route behavior: the editor is reachable on the mesh, and the Funnel
host reaches n8n only under webhook prefixes. An unknown webhook path returns
an n8n not-found response; a generic 404 without n8n webhook text does not prove
backend reachability. Also require Funnel root/admin denial, absence of the
retired helper hook, and fresh signed deliveries for the surviving Emergency
and Policy Bot callbacks. The internal database-aware health request from the n8n pod should
print `200` after the AuthorizationPolicy syncs. HTTP 503 with `Database is not
ready!` means the callback reached n8n but n8n cannot use PostgreSQL; inspect
both pods and confirm the database-aware liveness probe replaces the stale n8n
process.

## Rollback

Revert a failed application revision through GitOps while preserving the working
Funnel URL and surviving external registrations. A transport rollback needs a
separate reviewed route/URL change and fresh delivery verification; do not point
public webhooks at the private editor or restore the deleted DNS writer.
Retain the legacy routes until replacement acceptance. Preserve both the n8n
and `n8n-postgres` PVCs unless deliberately rebuilding from verified exports.
To roll back internal self-API access alone, remove the
`cluster.local/ns/automation/sa/n8n` principal through GitOps; dependent workflows
will fail, but persisted data is unchanged.
